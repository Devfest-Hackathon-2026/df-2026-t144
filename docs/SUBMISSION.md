## Google技術の採用理由(審査「1-b」用)

| 技術 | 何に使うか | 選んだ理由 | 比べて捨てた案 |
| --- | --- | --- | --- |
| Gemini(Vertex AI) | 「水路が好き」のような自由な言葉を6つの視点タグに分ける。次の「？」へ誘う一文を書く。視点別の解説を下書きする | 言い回しが人ごとに違う興味を、決まったタグに落とせる。JSONスキーマで出力させるので、使った事実のIDや数字をコードで検査できる | 解説のライブ生成(誤った年号を出しても止められない)。Geminiによる順位付け(順位の理由を説明できない)。Googleマップによるグラウンディング(日本語に未対応) |
| Routes API | 寄り道ありとなしの徒歩時間を比べ、「追加5分以内」を実際の道で守る | 寄り道の価値は「何分増えるか」で決まる。直線距離では嘘になる | Directions API(2025年3月にLegacy化し、新規プロジェクトで使えない) |
| Cloud Run | Web版とAPIを1つのサービスで配信する | 審査員がURL1つで触れる。アクセスがないときは0台で課金されない。サービスアカウントでGeminiを呼べるので、APIキーを持たずに済む | Firebase Hosting + 別のAPIサーバー(デプロイが2つになり、CORSの設定も要る) |

## Geminiの誤りをどう防ぐか(質疑用)

- Geminiに渡す情報は、出典を確認した事実(`facts`)だけ。
- ライブで出す一文は、表示前にコードで4点を検査する。①渡した事実のIDだけを使っているか、②本文の数字が使った事実に含まれているか、③次のスポット名を明かしていないか、④長さ。1つでも外れたら固定文を出す。
- 解説本文はライブ生成しない。事前に下書きし、人が出典と照合したものだけを出す。照合数は `pnpm stories:check` が数える。ピッチでは「N本を照合し、M本を却下」と数字で答える。
